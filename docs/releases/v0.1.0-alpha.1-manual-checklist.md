## Checklist

1. **Permission prompt.** \* Click **Start Conversation**. The browser asks for the microphone.
   Allow it. The status reaches **Listening** and you **hear** the welcome message.
2. **Permission denied.** \* Block the microphone in site settings (lock icon → Microphone →
   Block), reload, start. You get "Microphone access was blocked…" and no session stays open.
   Restore the permission afterwards.
3. **Audible output.** Ask "What are your opening hours?". The answer is clearly audible, matches
   the transcript word for word, and the visualiser moves while it speaks.
4. **Interruption.** Ask "How do I return an item?" and talk over the answer after a few words.
   Speech stops promptly, and the transcript shows only what was actually spoken.
5. **End while speaking (SDK patch).** Ask a question and click **End Conversation** while the
   answer is playing. The page shows "Conversation ended." and the console shows **no**
   `Uncaught DataStreamError`. In `pnpm --filter @voicebridge/web-example dev`, no Next.js error
   overlay appears.
6. **Fresh session after ending.** Start again. You hear the welcome message, the transcript starts
   empty, and the host log shows a new `token_issued`.
7. **Autoplay fallback.** \* In Chrome, site settings → Sound → Mute (or use a browser profile that
   blocks autoplay), then start. An **Allow audio playback** button appears; clicking it plays the
   assistant's audio. Restore the setting afterwards.
8. **Reconnection after a network interruption.** Interrupt the browser's network for about
   5 seconds, then for about 30 seconds (procedure below). Within about 20 seconds of restoring it,
   either the conversation continues (ask a question to confirm) or the page shows "The connection
   was lost…" and you can start a new conversation. It must **not** claim "The assistant ended the
   conversation" while the agent is still connected. Record which outcome you saw for each run.
9. **Microphone indicator.** After **End Conversation**, the browser's microphone-in-use indicator
   turns off.
10. **LiveKit dashboard privacy settings.** In the LiveKit Cloud dashboard for the project:
    - Under the project's Agent Observability or data settings, confirm that session recording,
      transcripts, and traces are disabled, or understand what's enabled. The worker passes
      `record: false` regardless.
    - Open the latest session in the dashboard. Confirm no audio recording or transcript is stored
      for it.
    - Note the project's data region and whether region restriction for Inference is on.

Record the date, browser and version, and the result of each item in the release issue or notes.
Mark anything you couldn't do as **not verified**.

## Item 8: network interruption

Cut the test machine's network (turn Wi-Fi off or unplug the cable) for the chosen time, then
restore it. Do this at the machine itself: a remote session to it would drop too. If the browser
and the four services run on the same machine, this also cuts the worker's connection to LiveKit.
To interrupt only the browser, run it on a second machine, or block only the browser's traffic
with your operating system's firewall (remove the rule afterwards).

### Before you start

1. Four services running, the page open in the browser, a conversation started, and one question
   answered.
2. In a terminal, note the worker's job count: `curl -s http://127.0.0.1:8081/worker` (it should
   report one active job).

### What to observe and record

- **Page:** status during the outage (expected: **Connecting** while reconnecting), then the
  outcome: the conversation continues (ask "How long does delivery take?") or "The connection was
  lost…". Never "The assistant ended the conversation" while the agent is connected.
- **Console:** no `Uncaught DataStreamError` and no other uncaught errors.
- **Host log:** no new `token_issued` during reconnection (the page never refetches credentials).
  A new one appears only when you click **Start Conversation** again.
- **Backend and worker after a terminal disconnect** ("connection lost", or End): the backend logs
  `session_ended`, and `curl.exe -s http://127.0.0.1:8081/worker` returns to zero active jobs.
  Record how long that took. It depends on LiveKit's participant timeout and room departure
  timeout, which haven't been measured for this project.
- **Worker log:** at the default `LOG_LEVEL=error` it contains no user text.

### Pass, fail, inconclusive

| Outcome          | Conditions                                                                                                                                                                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Pass**         | Both runs end in "continues" or "connection lost" within about 20 s of restoring the network; never a false "assistant ended"; no uncaught errors; a new conversation works afterwards; the job count returns to zero within 2 minutes of a terminal disconnect |
| **Fail**         | A false "assistant ended"; the page stuck in **Connecting** for more than 60 s with no final state; Start doesn't work afterwards; a job still active 5 minutes after a terminal disconnect; uncaught errors                                                                      |
| **Inconclusive** | Nothing changes on the page within 10 s of cutting the network. Check that the network was really cut, then repeat                                                                                                                                                                |
